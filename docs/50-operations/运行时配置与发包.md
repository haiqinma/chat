# 运行时配置与发包

本文档说明当前项目里配置的真实边界：哪些变量在打包时生效，哪些在服务启动时生效，哪些会继续下发到前端。

当前模板文件分为两份：

- `.env.template`：运行期模板
- `.env.build.template`：构建/发包模板

推荐配套文件：

- `.env`：Web/standalone 的实际运行期配置
- `.env.build`：构建/发包参数，以及桌面包首次启动时使用的服务默认值

## 1. 结论

当前项目按运行形态使用两份环境文件，桌面用户设置页覆盖能力另有明确的目标方案：

1. 构建/发包配置
   - 只放在 `.env.build`，由构建入口读取；命令行/CI 环境变量可以覆盖
   - 修改构建参数、桌面包出厂默认服务值或签名配置后需要重新构建/发包
2. Web standalone 运行期配置
   - Web Node 服务启动后从 `.env` 读取
   - 浏览器公开配置由服务端动态渲染的 `meta[name="runtime-config"]` 和 `/api/config` 下发
   - 修改 `.env` 后重启 Web 服务并刷新页面，不需要重新构建 Web 代码
3. 桌面用户运行期配置
   - 桌面版当前把 `.env.build` 的公开服务值作为包内默认值，尚无设置页覆盖功能
   - 目标是在 Chat 设置页保存用户覆盖值；该功能实现后，用户修改服务地址不需要重新打包

Web standalone 只在服务启动时读取 `.env` 作为运行配置；构建和发包过程不加载 `.env`。standalone 构建从 `.env.build` 读取 `BUILD_VERSION`、`DISABLE_CHUNK` 等构建参数；静态 export 和桌面构建还从 `.env.build` 读取要嵌入产物的公开默认值。Tauri 桌面构建不会继承 `.env` 中的 Web 运行配置。

统一优先级为：命令行/CI 环境变量 > `.env.build` > 代码默认值。Next 自身会扫描标准 `.env` 文件，项目构建加载器会隔离其中的变量；构建日志显示发现 `.env` 不表示其内容参与了产物配置。

布尔开关变量当前统一支持：

- `0` / `1`
- `false` / `true`

推荐统一使用 `0` / `1`。

因此现在的标准认识是：

- `.env` 只有 Web 开发和 standalone 服务运行期变量
- `.env.build` 是构建/发包配置的唯一文件来源
- standalone 部署产物在发包后仍然可以修改 `.env`
- 只要不是构建产物形态相关的变量，就不需要重新打包

## 2. 配置来源

### 2.1 构建期

构建元信息由 [app/config/build.ts](/Users/liuxin2/Workspace/opensource/chat/app/config/build.ts) 提供：

- `version`
- `commitDate`
- `commitHash`
- `buildMode`
- `isApp`

这些字段会被合并进前端公开配置，但它们的来源仍然是构建期。

其中 `version` 的当前规则是：

- 源码仓库本身不要求维护 `package.json.version`
- `BUILD_VERSION` 存在时优先作为构建版本，允许桌面静态导出和 Tauri 发包嵌入当前 release tag
- `scripts/package.sh` 会把当前 `TARGET_TAG` 注入为 `BUILD_VERSION`
- `standalone` 打包时由 `scripts/package.sh` 把当前 `TARGET_TAG` 写入产物目录里的 `package.json.version`
- 运行中的 standalone 服务只读取自己部署目录里的 `package.json.version`

构建相关模板变量现在放在 `.env.build.template`，实际构建时建议复制为 `.env.build` 使用。桌面包的出厂服务默认值也由该文件提供，但它们不是桌面用户的长期配置入口。
其中 `BUILD_MODE`、`BUILD_APP` 仍然属于构建期概念，但不再作为 `.env.build` 的手工配置项，而是由 `scripts/package.sh` 的 mode 或专用构建脚本决定。

### 2.2 服务端运行期

服务端私有配置由 [app/config/server.ts](/Users/liuxin2/Workspace/opensource/chat/app/config/server.ts) 读取。

这部分包括：

- 各模型供应商的 API Key / URL
- 访问控制与代理
- 工具运行时开关
- WebDAV 服务端代理配置
- 分析与基础设施配置

运行期模板变量现在放在 `.env.template`。

### 2.3 前端公开运行期

前端公开配置由 [app/config/runtime.ts](/Users/liuxin2/Workspace/opensource/chat/app/config/runtime.ts) 组装，在服务端渲染时注入：

- 页面首屏通过 `meta[name="runtime-config"]` 读取
- 客户端后续也可以通过 `/api/config` 获取最新公开配置

相关入口：

- [app/layout.tsx](/Users/liuxin2/Workspace/opensource/chat/app/layout.tsx)
- [app/api/config/route.ts](/Users/liuxin2/Workspace/opensource/chat/app/api/config/route.ts)
- [app/config/client.ts](/Users/liuxin2/Workspace/opensource/chat/app/config/client.ts)

- `CENTRAL_UCAN_AUTH_BASE_URL` 是 Node 认证服务地址
- 发布桌面包时，`CENTRAL_UCAN_AUTH_BASE_URL` 必须是用户可访问的公网 HTTPS 地址，不能使用 `localhost`、`127.0.0.1` 或其他回环地址；这些地址只适用于本地开发
- `CENTRAL_UCAN_REDIRECT_URI` 是 Web 授权完成后的回调地址，必须和 Node 应用配置里的某一项 `redirectUris` 完全一致；桌面包固定使用 `chat://localhost/central-ucan-callback.html`
- GitHub Actions 不会读取开发机的 `.env.build`。发布桌面包时，必须在 Repository Variables 中配置 `ROUTER_BACKEND_URL`、`WEBDAV_BACKEND_BASE_URL`、`CHAT_APPLICATION_UID`，并按需配置 Router Portal 地址；三个桌面构建 job 会显式注入这些变量。

- `.github/workflows/app.yml` 优先读取同名 GitHub Repository Variable，默认使用 `chat://localhost/central-ucan-callback.html`。如已配置该变量，需将其更新为此精确地址。本地打包仍需在环境变量中配置此地址。Node 应用市场必须登记完全相同的回调地址。
- Tauri 桌面本地包的回调地址应使用 `chat://localhost/central-ucan-callback.html`，不要改成 `http://localhost:8100` 或 `https://tauri.localhost/...`
- 桌面端登录会在系统浏览器中打开 Node 验证页；验证完成后由操作系统通过 `chat://` 协议唤回 Chat，再由 Chat 使用 PKCE 授权码交换完成登录。Node 服务本身仍必须可从用户网络访问；`https://tauri.localhost` 仅是 Tauri WebView 的页面 origin，不是外部回调地址。
- `ROUTER_PORTAL_URL` 默认回退到 `https://router.yeying.pub`
- `ROUTER_PORTAL_TOKEN_URL` 未配置时继承 `ROUTER_PORTAL_URL`
- `ROUTER_PORTAL_RECHARGE_URL` 未配置时继承 `ROUTER_PORTAL_TOKEN_URL`

## 4. 发包后的正确操作

### 4.1 package.sh 模式

当前 [scripts/package.sh](/Users/liuxin2/Workspace/opensource/chat/scripts/package.sh) 已经是统一打包入口，支持以下模式：

- `standalone`：Node 服务部署包
- `export`：静态导出包
- `app`：桌面端构建产物包
- `app-release`：桌面端 updater release 产物包

这里的 `mode` 是以下构建期行为的唯一来源：

- `BUILD_MODE`
- `BUILD_APP`

常用参数：

- `--output-dir DIR`：指定打包产物输出目录，默认是仓库下的 `output/`

默认 mode 解析顺序：

1. 命令行显式传入的 `MODE`
2. 仓库根目录的 `build.mode`
3. 默认值 `standalone`

依赖安装规则：

- 每次执行 `scripts/package.sh` 都会先同步依赖
- 存在 `package-lock.json` 时运行 `npm ci`
- 否则运行 `npm install`

示例：

- `bash scripts/package.sh`
- `bash scripts/package.sh standalone`
- `bash scripts/package.sh export v1.2.3`
- `bash scripts/package.sh app`
- `bash scripts/package.sh app-release`
- `bash scripts/package.sh standalone --output-dir ./dist`

### 4.2 standalone 部署

推荐流程：

1. 通过现有发包流程生成 standalone 产物
2. 构建前，如需切换构建细节变量，先从 `.env.build.template` 复制出 `.env.build`
3. 按构建目标修改 `.env.build`
4. 部署时，从 `.env.template` 复制出 `.env`
5. 按部署环境填写 `.env`
6. 启动服务

后续如果只是修改运行期变量：

1. 更新 `.env`
2. 重启服务
3. 刷新页面

不需要重新打包。

### 4.3 standalone 打包流程

standalone 模式推荐流程：

1. 构建前，如需切换构建细节变量，先从 `.env.build.template` 复制出 `.env.build`
2. 按构建目标修改 `.env.build`
3. 部署时，从 `.env.template` 复制出 `.env`
4. 按部署环境填写 `.env`
5. 执行 `bash scripts/package.sh standalone`
6. 在产物目录中使用 `scripts/starter.sh` 启动服务

补充：

- 打包脚本会自动把当前 tag 写入 standalone 产物目录里的 `package.json.version`
- 因此生产部署时不需要再手工设置版本环境变量
- 如果线上只是版本读取异常，也可以直接修复部署目录里的 `package.json.version` 临时止血

### 4.4 什么时候必须重新打包

以下情况需要重新构建；桌面端场景通常还要重新发包：

- 切换 `scripts/package.sh` 的 mode
- 修改 `DISABLE_CHUNK`
- 修改 Tauri 签名参数
- 变更代码、依赖、静态资源
- 修改桌面包的出厂服务默认值，例如 `ROUTER_BACKEND_URL`、`WEBDAV_BACKEND_BASE_URL`、`WEBDAV_BACKEND_PREFIX`、`CENTRAL_UCAN_AUTH_BASE_URL`
- 修改桌面固定应用身份 `CHAT_APPLICATION_UID` 或回调协议 `CENTRAL_UCAN_REDIRECT_URI`
- 任何影响 Next / Tauri 产物形态的配置

桌面设置页的服务地址覆盖功能尚未实现。实现后，通过设置页保存的 Router、Warehouse/WebDAV、Node 地址将不再要求用户重新打包；改 `.env.build` 仍然只会改变后续安装包的出厂默认值。

### 4.5 桌面本地包配置流程

当前桌面本地包需要先从模板创建 `.env.build`，并在其中配置桌面包内的服务默认值：

```dotenv
ROUTER_BACKEND_URL=http://localhost:3011
WEBDAV_BACKEND_BASE_URL=http://localhost:6065
WEBDAV_BACKEND_PREFIX=/dav
CHAT_APPLICATION_UID=<Node 中 Chat 应用的 applications.uid>
CENTRAL_UCAN_AUTH_BASE_URL=http://localhost:8100
CENTRAL_UCAN_REDIRECT_URI=chat://localhost/central-ucan-callback.html
```

由于设置页覆盖功能尚未实现，当前修改这些地址后仍需重新打包并打开：

```bash
npm run app:build
open src-tauri/target/release/bundle/macos/Chat.app
```

桌面端打包脚本会在构建开始前校验 Node 身份授权配置。以下配置均为必填，且回调地址必须完全匹配：

```dotenv
CENTRAL_UCAN_AUTH_BASE_URL=http://localhost:8100
CENTRAL_UCAN_REDIRECT_URI=chat://localhost/central-ucan-callback.html
```

登录入口固定采用自动策略：先尝试 Wallet Identity Presentation，钱包不可用时再进入 Node Passkey 授权。发布仓库变量 `CENTRAL_UCAN_AUTH_BASE_URL` 和 `CHAT_APPLICATION_UID` 必须已配置，且认证地址不能是本机回环地址。

其中：

- `ROUTER_BACKEND_URL` 指向 Router，不指向 Node
- `CENTRAL_UCAN_AUTH_BASE_URL` 指向 Node
- `WEBDAV_BACKEND_BASE_URL` 指向 Warehouse
- `CHAT_APPLICATION_UID` 是 Node 应用中心 Chat 应用的 `applications.uid`；Web、桌面和其他同一应用客户端必须复用它
- `CENTRAL_UCAN_REDIRECT_URI` 决定 Node 授权完成后回到桌面应用的地址

如果桌面端和 web 端要共享历史 `/apps/<旧ID>` 数据，必须先确认该目录属于哪个 Chat 应用 UID，再迁移目录到新的稳定 UID；不能把 Warehouse UID 当成 Chat UID。

## 5. 配置使用原则

当前实现遵循下面几条边界：

1. `build.ts` 保留真正的构建元信息
2. `server.ts` 负责 Web 服务端私有配置
3. `runtime.ts` 负责浏览器可见的公开运行配置
4. Secret 不进入 `runtime-config`，也不进入 `/api/config`
5. Web standalone 的公开运行配置由运行中的服务提供；桌面版当前使用包内默认配置，设置页覆盖是目标行为，落地前不能假定已经支持

## 6. 排障方法

### 6.1 看变量属于哪一层

先判断问题变量属于哪类：

- build: 重建才会变
- Web server runtime / public runtime: 更新 `.env`、重启 Web 服务并刷新页面
- Desktop package defaults: 更新 `.env.build` 并重新打包；设置页覆盖功能落地后，用户服务地址由桌面端本地设置管理

### 6.2 验证前端实际拿到的公开配置

可以检查：

- 页面里的 `meta[name="runtime-config"]`
- `GET /api/config` 返回值

如果两者都没更新，优先检查：

1. 服务是否已经重启
2. 启动脚本是否正确加载了新的 `.env`
3. 页面是否仍在使用旧标签页缓存

## 7. 已知事项

### 7.1 export 模式限制

`BUILD_MODE=export` 仍受 Next 静态导出约束影响。  
仓库里某些 API 路由本身不适合静态导出，这属于既有约束，不是这次配置拆分引入的问题。

### 7.2 standalone 版本号说明

源码仓库默认允许 `package.json` 没有 `version` 字段。  
因此在未经过 `scripts/package.sh` 的本地源码环境里，`build.ts` 读取不到版本时会回退成 `v0.0.0`。

这不影响 standalone 正式部署，因为正式产物会在打包时自动写入真实 tag 版本。

### 7.3 桌面端版本号说明

桌面端是静态导出产物，前端公开配置会在构建时固化到 `out/`。
正式发包时必须通过 `scripts/package.sh app` / `scripts/package.sh app-release`，或显式设置 `BUILD_VERSION=v<major>.<minor>.<patch>`，否则本地源码构建仍可能显示 fallback 版本。

`scripts/tauri-build-app.mjs` 会用 `BUILD_VERSION` 或 GitHub release tag 生成临时 Tauri 配置覆盖版本号，不要求每次 release 都手工修改 `src-tauri/tauri.conf.json`。
